A developer needs a new environment: a subscription, a resource group in it, a key vault in that
group. Each piece is owned by a different team, maybe in a different GitHub organization. With
Zekt, the developer's workflow sends **one request**. Each team's own workflow does its part, in
its own repository, and the result comes back to the developer.

<OrchestrationFlow />

## What Zekt takes off your hands

Without a broker, every pair of repositories needs its own wiring. The calling repository needs a
token or GitHub App with access to the other repository. It has to trigger the other workflow, wait
for the run, and find a way to read its result. That's repeated for every team and every step, and
handled differently each time.

With Zekt, the requesting workflow names the services it wants, in order or in parallel, and Zekt
does the rest:

| | Wiring it yourself | With Zekt |
| --- | --- | --- |
| **Secrets in the calling workflow** | A token or app with access to each target repository | None. Your workflow holds no credentials for the repositories that do the work, and the [Zekt Action](/zekt-docs/provider/zekt-action/) signs in with GitHub Actions OIDC |
| **Who may call a service** | Whoever holds the token | The service owner approves each account's [access](/zekt-docs/provider/access-requests/), by hand or by rule |
| **Passing results on** | Custom glue per step | Each step's outputs feed later steps with `$zekt{{ steps.<id>.outputs.<field> }}` |
| **Knowing how it went** | Read each run yourself | One result event, plus step-by-step tracking in the console |

## Who it's for

**Developers who request services.** Ask for what you need in one workflow step. You don't need to
know how each team provisions things, and you don't need access to their repositories.

**Platform and service teams.** Turn a workflow you already have into a service other teams can
call. Your business logic stays in your own workflow YAML: Zekt dispatches the request and carries
the outputs, but never dictates what your workflow does. You decide who may call it, and you see
who calls it and how each call went.

## What a request looks like

The requesting workflow sends a plan to the Zekt Action. Here, the second step uses the first
step's output:

```json
{
  "default_service_owner": "platform-team",
  "services": [
    { "step_id": "create-sub", "service_slug": "new-subscription", "input": { "name": "team-a" } },
    {
      "step_id": "create-rg",
      "service_slug": "new-resource-group",
      "input": { "subscriptionId": "$zekt{{ steps.create-sub.outputs.subscription_id }}" }
    }
  ]
}
```

[Orchestrate several services](/zekt-docs/orchestration/overview/) shows the full workflow, the plan
fields and the result event.

## Good to know

- The requesting repository is [enabled as a provider](/zekt-docs/provider/enable-repository/), and
  your account has an approved subscription to each service in the plan.
- The account that starts the orchestration pays for all of it. See
  [zekt.dev/zekt-pricing](https://www.zekt.dev/zekt-pricing.html).
- For the other limits, see [Limits](/zekt-docs/orchestration/overview/#limits).

<Aside type="caution" title="Inputs and outputs aren't for secrets">
	[Zekt Shield](/zekt-docs/add-ons/shield/) doesn't encrypt orchestration inputs and outputs. Pass
	names and identifiers, not credentials. Each service keeps its secrets in its own repository.
</Aside>
