These scenarios show where Zekt replaces shared credentials, custom webhook code or manual handoffs.
Each one fits in a few workflows.

## Notify partners when something changes

**Scenario.** A sneaker manufacturer wants retailers to know about new models as soon as they're
announced, so the retailers can prepare listings, update inventory and plan marketing.

**Without Zekt** the manufacturer publishes product data through an API. Then it hands out
credentials, documents the integration, and keeps the API running, while each retailer builds and maintains a client.

**With Zekt:**

1. The manufacturer's product pipeline is a provider service. When it runs, it attaches the product
   data to the event with the [Zekt Action](/zekt-docs/provider/zekt-action/).
2. Retailers find the service in the Directory and request access. The manufacturer approves them.
3. Every approved retailer's workflow runs on the `repository_dispatch` event and reads the payload.

No credentials change hands, and the manufacturer runs no API. You can look at a live example in the
[Zekt Registry](https://www.zekt.dev/zekt-registry.html) (*Zekt Sneakers*) and in the
[provider example repository](https://github.com/zekt-dev-org/zekt-provider-example-repo).

## Send failed security scans to an audit team

**Scenario.** A failed security scan must be reviewed by a separate audit team that works in a
different repository or organization.

**Without Zekt** the hand-off is an email, a Slack message or a ticket. It depends on someone
noticing, and it's hard to trace afterwards.

**With Zekt:**

1. The scanning pipeline sends an event (and the findings as a payload) when a scan fails.
2. Zekt delivers it to the audit team's repository, which starts their review workflow.
3. The audit team never needs access to the scanned repository.

Every delivery is tracked with a correlation ID. With [Zekt Analytics](/zekt-docs/add-ons/analytics/),
you can replay past events to test changes to the audit workflow.

<Aside type="tip">
	Findings can be sensitive. With [Zekt Shield](/zekt-docs/add-ons/shield/), the payload is encrypted
	in the provider's workflow, so only the audit team can read it. Zekt can't read it.
</Aside>

## Automate a process that spans several organizations

**Scenario.** A supply-chain, approval or onboarding process has steps owned by different teams or
companies, each with its own repositories.

**Without Zekt** the steps are joined together by people, scripts and custom webhooks. Steps get missed or
run out of order, and nobody can see the whole process.

**With Zekt:**

1. Each step is a GitHub workflow. When it finishes, it sends an event.
2. Zekt routes the event to the team that owns the next step, whose workflow starts automatically.
3. A step that has to receive *and* send events uses [Zekt Chainlink](/zekt-docs/add-ons/chainlink/).
   With Chainlink, a chain can run through several organizations and even loop back to where it started.

GitHub Actions does the work. Zekt routes events between the steps and tracks every delivery.

If one workflow needs to call several services in a fixed order and collect their results, see
[Orchestration](/zekt-docs/orchestration/overview/).
