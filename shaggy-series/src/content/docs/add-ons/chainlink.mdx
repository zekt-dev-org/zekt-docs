Normally a repository is either a provider or a consumer. **Chainlink** lets one repository be
both: it receives events from upstream services and sends its own events downstream. That way,
events can chain across repositories: A → B → C, across organizations if needed.

## Who does what in a chain

| Link | What it is | Needs Chainlink? |
| --- | --- | --- |
| **First** (A) | An ordinary [provider service](/zekt-docs/provider/workflows-and-services/). Its workflow sends an event with the [Zekt Action](/zekt-docs/provider/zekt-action/), exactly as without a chain. | No |
| **Middle** (B) | A **relay**: it receives the event from the link before it, decides what to pass on, and sends its own event to the next link. It's a consumer and a provider at once. | Yes |
| **Last** (C) | An ordinary consumer that [receives events](/zekt-docs/consumer/receive-events/) and doesn't send any further. | No |

So only the links in the middle are Chainlink repositories. A relay usually does one of three things
with what it receives:

- **forwards** it as it is;
- **reduces** it, removing information the next link shouldn't get;
- **enriches or transforms** it into what the next step needs.

[Forward, reduce or enrich](#forward-reduce-or-enrich) shows each one.

## Requirements

Your account needs the **Both** persona. Otherwise the Chainlink sidebar item is hidden, and
enabling gives *Chainlink requires a dual-role (both provider and consumer) account*.

## Enable a repository

<Steps>

1. Go to **Chainlink → Repos** and choose **Enable** on the repository.
2. Only one side (provider or consumer) needs to exist already. Zekt creates the other side
   automatically, with no second GitHub App installation.

</Steps>

The Chainlink section has three tabs: **Overview**, **Repos**, and **Topology**, a graph of your
chains that marks whether each hop changed the payload.

## How a chain works

Zekt never changes a payload in transit. Each repository in the chain runs its own workflow:

- **To pass an event on**, the middle repository's workflow sends a new event with the
  [Zekt Action](/zekt-docs/provider/zekt-action/).
- **To enrich or reduce the data**, that workflow builds the new payload itself.
- **To hold an event for approval**, use GitHub environment protection rules in that workflow.
- [Redaction Guard](/zekt-docs/add-ons/shield/#redaction-guard) scans every outgoing provider payload,
  so it also covers what a relay repository sends.

### When Zekt relays

When a run in the Chainlink repository that was triggered by `repository_dispatch` completes, Zekt
relays it downstream only if **all** of these hold:

1. The run called the [Zekt Action](/zekt-docs/provider/zekt-action/). Completion alone never relays.
2. The run isn't an orchestration step.
3. The relay workflow is whitelisted.
4. The message wasn't blocked, for example by a Shield requirement.
5. Your account is in good standing.

Then:

- **Subscribers** to the relay workflow's provider service get the event, even if the relay run
  failed, so they should check its conclusion.
- **Consumer services** the relay workflow fires into get it too, unless the relay run failed.

### What goes downstream

- The event type and `zekt.payload` are the **relay's own**. The inbound payload is **not** forwarded
  automatically, so copy what you need into the new payload.
- `workflow_run` describes the relay's run, and downstream branch filters match the relay run's
  branch.
- The downstream `correlationId` belongs to the relay's run.

### The first link

The chain starts with an ordinary provider workflow. Nothing in it is specific to Chainlink: its
event type is what the first relay listens for.

```yaml
name: Build
on:
  push:
    branches: [main]
permissions:
  id-token: write
  contents: read
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: echo "build and push the image here"
      - uses: zekt-dev-org/zekt-action@v3
        with:
          event-type: build-complete
          payload: |
            {
              "image": "ghcr.io/acme/web:${{ github.sha }}",
              "commit": "${{ github.sha }}",
              "requested_by": "${{ github.actor }}"
            }
```

### A relay workflow

Before you start:

- this repository subscribes to the upstream service, as its consumer repository;
- this workflow is published as a provider service that downstream accounts subscribe to;
- the workflow is whitelisted.

```yaml
name: Relay build events
run-name: ${{ github.event.client_payload.zekt.dispatch_id }}
on:
  repository_dispatch:
    types: [build-complete]          # the upstream service's event type
permissions:
  id-token: write
  contents: read
jobs:
  relay:
    runs-on: ubuntu-latest
    steps:
      - name: Build downstream payload
        id: build
        env:
          INBOUND: ${{ toJSON(github.event.client_payload.zekt.payload) }}
          UPSTREAM_CONCLUSION: ${{ github.event.client_payload.workflow_run.conclusion }}
        run: |
          payload=$(jq -c --arg c "$UPSTREAM_CONCLUSION" '{upstream: ., upstream_conclusion: $c}' <<<"$INBOUND")
          echo "payload=$payload" >> "$GITHUB_OUTPUT"
      - uses: zekt-dev-org/zekt-action@v3
        with:
          event-type: build-relayed    # what downstream subscribers receive
          payload: ${{ steps.build.outputs.payload }}
```

<Aside type="caution" title="Set run-name to the inbound dispatch_id">
	Zekt works out how many hops an event has taken by matching the relay's run to the event that
	triggered it. Without `run-name` set to `client_payload.zekt.dispatch_id`, the relay counts as the
	start of a new chain.
</Aside>

### Forward, reduce or enrich

The relay decides what goes downstream in its **Build downstream payload** step. Swap that step's
`jq` line for the one you need. Each reads the inbound payload from `INBOUND`, as in the workflow
above.

**Forward as is**: the next link gets the same data.

```bash
payload=$(jq -c . <<<"$INBOUND")
```

**Reduce**: remove what the next link shouldn't see, such as who requested the build.

```bash
payload=$(jq -c 'del(.requested_by)' <<<"$INBOUND")
```

**Enrich or transform**: reshape the data for the next step, and add what this link knows.

```bash
payload=$(jq -c --arg env "staging" '{image: .image, environment: $env, approved: true}' <<<"$INBOUND")
```

Whichever you choose:

- The inbound payload isn't forwarded unless you put it in the new payload. Zekt doesn't change it on
  the way.
- Pass the inbound payload to your script through `env`, as above, rather than writing
  `${{ github.event.client_payload… }}` inside `run:`. Its content then can't be run as part of the
  script.
- `zekt.payload` is `null` when the link before sent none. If that link uses
  [Shield](/zekt-docs/add-ons/shield/), it's the encrypted envelope, not the data:
  [decrypt it](/zekt-docs/add-ons/shield/#decrypt-in-your-workflow) before you reduce or reshape it.
- [Redaction Guard](/zekt-docs/add-ons/shield/#redaction-guard) still scans what the relay sends.

## Hop limit

The payload carries no hop information. Zekt tracks hops itself, and the dashboard shows *Hop N of M*
on deliveries.

- The original sender's delivery is hop 0, and each relay adds 1.
- Each Chainlink repository has its own **maxHops**, from **2 to 10**, set in the **Repos** tab. A relay
  can send only while its outgoing hop is below its own maxHops, so the *k*-th relay in a chain needs
  maxHops of at least *k* + 1.
- When a relay is past its hop limit, the downstream send isn't made. It shows as *Not sent*, with the
  hop limit as the reason, in the [dispatch queue](/zekt-docs/operate/deliveries/#dispatch-queue).
- The hop limit doesn't apply to consumer services a relay fires into.

<Aside type="caution" title="The default is 2">
	With the default maxHops of 2, only the **first** relay in a chain can forward. Raise maxHops on
	later relays.
</Aside>

## Disable Chainlink

When you disable Chainlink on a repository, you choose which role to keep. Keeping only the consumer
role is refused while the repository's services still have active subscribers.

## Cost

A flat monthly fee per Chainlink repository, **instead of** the normal per-repository fee.
[Analytics](/zekt-docs/add-ons/analytics/) or [Shield](/zekt-docs/add-ons/shield/) on a Chainlink
repository is charged once, not per side. See
[zekt.dev/zekt-pricing](https://www.zekt.dev/zekt-pricing.html).

<Aside type="tip">
	Many processes only need one step: a provider sends and consumers receive. Use Chainlink when a
	repository genuinely needs to receive *and* send.
</Aside>
