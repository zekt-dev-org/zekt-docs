A **consumer service** turns the usual direction around. Other accounts send events *into* one of
your repositories, typically to ask for work to be done ("scan this image", "create a resource
group"). Consumer services are commonly called from [orchestration](/zekt-docs/orchestration/overview/),
and can return outputs to the caller.

## Requirements

- Your account has the **Both** persona. The **Consumer Services** sub-tab is shown only to accounts
  with Both. Upgrade under **Profile → Persona & Access**.
- The repository behind the service is an active consumer repository with **Track Completion** on.
- The service is enabled.

## Create the service

<Steps>

1. Go to **Provider → Service Descriptions → Consumer Services**.
2. Fill in the form (see below).
3. Choose **Create Consumer Service**. Use **Reset** to clear the form.

</Steps>

| Field | What it's for |
| --- | --- |
| **Consumer Repository** * | The repository that receives the requests. Only active consumer repositories are listed. |
| **Service Name** * | Up to 100 characters. |
| **Publisher Name** | Up to 50 characters. |
| **Description** | What the service does, for people browsing the Directory. |
| **Event Direction** * | *Subscribers fire events to me*. |
| **Dispatch Event Type** | The event type your workflow listens for. |
| **Service Slug (Optional)** | The slug orchestration plans use. Lowercase kebab-case, 2–64 characters. Immutable once set. |
| **Supports Orchestration** | Declares that the service is meant to be orchestrated. It's a declaration, not a gate: an undeclared service can still be orchestrated, and the requester gets a warning. |
| **Service Tags** | Help people find the service. |
| **Publish to Directory** | Choose **Public** or **Organization**. A new consumer service starts at Organization, and Zekt asks you to confirm before making one Public. See [visibility](/zekt-docs/provider/publish-to-directory/). |

After the service is created, you can add an avatar. In edit mode, you can publish an
[input and output schema](/zekt-docs/provider/schemas/) so callers know what to send and what they'll
get back.

A consumer service receives events in two ways:

- [from subscribers' workflows](#when-subscribers-fire-events-into-it), when a run of their approved
  workflow completes; and
- [as an orchestration step](#when-called-from-an-orchestration), when someone's orchestration calls it.

## When subscribers fire events into it

### Who can fire

A subscriber requests access with **one** workflow in one of its **provider** repositories. The request
form lists only those repositories, and each additional workflow needs its own request. The normal
access rules apply: the service's audience, a [Shield](/zekt-docs/add-ons/shield/) key if the
service requires Shield, Doctrine, and your approval by hand or by rule.

When you approve, the subscriber's workflow is whitelisted automatically. If it isn't, the subscriber
can whitelist it in **Provider → Workflows**. You approve these requests in **Provider → Access**,
where they're badged *Consumer service*. Approving one needs the Both persona.

### When an event fires

- An event fires when a run of the subscriber's approved workflow **completes**. A Zekt Action call
  on its own doesn't fire it.
- A run that concludes **failure** doesn't fire. Other conclusions, including *cancelled* and
  *timed_out*, do, so check `workflow_run.conclusion`.
- A run that submitted an orchestration doesn't fire subscriber events.
- The subscriber's account pays for firing, and must be in good standing. See
  [zekt.dev/zekt-pricing](https://www.zekt.dev/zekt-pricing.html).
- [Inquisition](/zekt-docs/consumer/inquisition/) filter rules don't apply to these events.

The Zekt Action call is optional. It decides what you receive:

- **With it**, you receive the action's `event-type`, and its `payload` as `client_payload.zekt.payload`.
  Only the first call in a run counts.
- **Without it**, the event type is `zekt-workflow-completed`, and there's no payload.

<Aside type="caution" title="The service's event type isn't applied">
	You receive whatever `event-type` the subscriber's workflow sent, not the type the service declares.
	Tell subscribers which event type to send, and list every type you accept in your workflow's
	`types:`, including `zekt-workflow-completed` if you accept runs without the Zekt Action.
</Aside>

### The subscriber's workflow

This must be the workflow chosen in the access request:

```yaml
name: Fire order event
on:
  push:
    branches: [main]
  workflow_dispatch:
permissions:
  id-token: write
  contents: read
jobs:
  fire:
    runs-on: ubuntu-latest
    steps:
      - name: Build payload
        id: payload
        env:
          SHA: ${{ github.sha }}
          REF: ${{ github.ref_name }}
        run: |
          json=$(jq -cn --arg sha "$SHA" --arg ref "$REF" '{sha: $sha, ref: $ref}')
          echo "json=$json" >> "$GITHUB_OUTPUT"
      - uses: zekt-dev-org/zekt-action@v3
        with:
          event-type: order-placed   # the service's declared event type
          payload: ${{ steps.payload.outputs.json }}
```

If the Zekt Action step fails, the run concludes *failure*, and nothing fires.

### What your repository receives

A `repository_dispatch` to the service's consumer repository. The event type is available as
`github.event.action`. `client_payload` contains:

- `workflow_run`: `id`, `name`, `conclusion`, `status`, `head_branch`, `event`, `created_at`,
  `updated_at`. These describe the **subscriber's** run.
- `repository`: `is_private` only.
- `zekt`: `correlationId`, `dispatchedAt`, `serviceOrigin` (`consumer`), `eventDirection`
  (`SubscriberFires`), `dispatch_id`, `payload` (left out entirely when the subscriber sent none),
  and `schemaVersion`/`schemaValid` when you enforce a schema.

The firing repository's name isn't in the payload. You see it in Zekt, on the delivery record and on
the access request. Don't trust identity fields a subscriber puts in its payload.

```yaml
name: Handle subscriber events
run-name: ${{ github.event.client_payload.zekt.dispatch_id }}
on:
  repository_dispatch:
    types: [order-placed, zekt-workflow-completed]
jobs:
  handle:
    runs-on: ubuntu-latest
    steps:
      - name: Read the event
        env:
          EVENT_TYPE: ${{ github.event.action }}
          CORRELATION_ID: ${{ github.event.client_payload.zekt.correlationId }}
          SENDER_CONCLUSION: ${{ github.event.client_payload.workflow_run.conclusion }}
          ORDER_REF: ${{ github.event.client_payload.zekt.payload.ref }}
        run: echo "Received $EVENT_TYPE ($CORRELATION_ID), sender run: $SENDER_CONCLUSION, ref: $ORDER_REF"
```

Put this workflow on the default branch. Setting `run-name` to the `dispatch_id` lets Zekt match the
run exactly.

### Following the events

- The subscriber sees its sends in **Provider → Delivery Status**. You see them in
  **Consumer → Received Events**.
- Statuses: dispatched, sent (completion not tracked), failed, schema blocked (if you
  [enforce a schema](/zekt-docs/provider/schemas/#enforce-a-schema)), confirmed and completed.
- Nothing is sent or held while the service is disabled or its repository is switched off.

## When called from an orchestration

### What your workflow receives

- `event_type`: the service's event type, or `zekt-workflow-completed` if it has none.
- `client_payload.input`: the input the caller sent.
- `client_payload._zekt`: orchestration context (`orchestration.executionId`,
  `orchestration.stepId`, `orchestration.requestorRepository`) and `dispatch_id`.

<Aside type="note">
	As the service owner, you see the name of the repository that called you.
</Aside>

### Report outputs

Call the Zekt Action **without** `event-type`. It detects the orchestration context by itself, and
its `payload` (a JSON object) becomes the step's outputs.

```yaml
name: security-scan service
on:
  repository_dispatch:
    types: [security-scan]
permissions:
  id-token: write
  contents: read
jobs:
  scan:
    runs-on: ubuntu-latest
    steps:
      - id: scan
        env:
          IMAGE: ${{ github.event.client_payload.input.image }}
        run: echo "verdict=pass" >> "$GITHUB_OUTPUT"
      - uses: zekt-dev-org/zekt-action@v3
        with:
          payload: |
            {"verdict":"${{ steps.scan.outputs.verdict }}","findings":0}
```

- Only the run Zekt dispatched can report outputs. If it calls the action several times, the last
  call wins.
- Return scalar values (strings, numbers, booleans): the Zekt Action exposes outputs as strings.
- The step's result follows the GitHub run's conclusion. A run that reports outputs and then fails
  still fails the step.

## Disabling the service

Disabling a consumer service hides it, refuses new requests, and **drops** subscriber events: they
aren't held for later. Subscriptions are kept, and re-enabling the service restores everything.
